# Claude Code / Codex 会话通信修复

## 原因

1. 项目品牌迁移后，本机共享通信 Skill 仍读取旧环境变量。新版进程已提供 `CREWVELA_CLI`、`CREWVELA_SESSION_ID`，但旧指南使 Claude 误判自己不是受管会话。
2. 同步指南后，Claude 成功投递到原 Codex。Codex 使用 CLI 回信时，默认只读沙箱禁止写入应用 outbox，停在额外权限审批；此前“可启动”修复没有恢复这一分支的自动通信。

## 修复

- 为受管 Codex 注入 `crewvela_sessions` stdio MCP，只提供 `sessions` / `send` 两个工具。MCP 子进程由宿主启动，消息操作沿用现有队列、目标解析、限流、就绪判断及 PTY 投递；不向工具提供 shell 或任意文件操作。
- 发送方固定绑定启动时的应用会话身份。拒绝额外发送方参数、失效身份、已停止的发送方及不合法消息。同一连接内近期重复请求返回原结果，不重复创建消息。
- Skill 优先使用该工具；没有此工具的 Claude 等运行时继续使用原 CLI。排队只代表接受消息，不得据此编造对方回复。
- 程序启动时同步已识别的旧版标准指南，兼容共享目录 junction，精确备份旧内容后替换。自定义指南、符号链接文件和 Skill 中心托管部署保留，后者仍由原更新事务管理。
- 没有修改用户全局 Codex 沙箱、审批或 MCP 配置，没有代用户批准权限。此前用户在旧进程批准 CLI 写入后，旧路径确实也完成过一次回信；新通道的验证使用 MCP，未依赖 shell 写入批准。

## 范围与限制

- 本次稳定的消息身份是**应用会话 ID**。核验时观察到，既有普通 Codex 恢复逻辑未总是恢复同一个原生 thread；原历史文件仍保留。本次没有修改该历史恢复逻辑，不能将消息往返通过表述为原生历史恢复已验收。
- 手动恢复同名记录时，曾打开另一个已停止历史条目；核对 ID 后立即停止，未向该条目发消息，未创建或删除会话。最终验收仅针对上述两个已核对的原应用 ID。
- 自定义/Skill 中心托管指南不会自动覆盖；需由其原管理方式同步。只有新启动的受管 Codex 会加载新 MCP，旧进程不能热更新。
- 未验证 macOS/Linux 原生进程，也未为其他运行时新增 MCP 通道。现有 CLI 与显式只读最小 outbox 授权的回归仍通过。
