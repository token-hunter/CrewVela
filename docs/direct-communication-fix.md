# 右侧多智能体面板通信修复

## 复现与根因

在多智能体面板选择 Claude Code 和 Codex 并请求互相打招呼，出现 Claude 无响应、Codex 目录落到 `C:\Windows`、以及向自身排队发送的情况。

1. 项目根目录经过 Windows canonicalize 后含 `\\?\` 前缀，CMD shim 不支持该工作目录，会退回 Windows 目录。独立 CMD 进程与实际 PTY 均复现；不是只检查字符串。
2. 多个桌面进程共享会话事件目录。旧实现即使不认识事件中的会话，也会删除其 SessionStart 事件，所属实例因此收不到就绪信号。两个隔离 SessionManager 的交错消费测试复现。
3. 统一协作指令没有标注当前接收者的身份，将包含自身的同一参与者列表发给所有人；MCP/CLI 也允许向绑定身份自身发送，导致误操作被当作成功排队。

## 修复

- 复用已有 Windows 外部路径转换，规范化 PTY 工作目录及 Codex 配置探测目录，不调整 sandbox、审批或账户权限。
- 不能识别所属会话的实例保留事件，交给真正的所属实例处理。
- 桌面主程序在初始化队列和会话状态前，持有数据目录的进程锁；重复实例提示退出，独立 CLI/钩子/MCP 子命令不受锁影响。锁随文件句柄释放，不通过删除锁文件判断进程退出。
- 为每位参与者分别包装指令，明确当前身份，只列出其他参与者；优先使用已经绑定发送者身份的会话 MCP。没有该工具时才回退至 Skill/CLI。
- MCP/CLI 拒绝自发自收，失败时不创建 outbox 消息。人工未绑定身份的发送、定向发送和原队列机制保留。

## 升级和验收边界

旧版本不持有新锁，无法在保持其运行的同时保证共享队列不被消费。升级前需从所有旧窗口或托盘菜单选择“退出”，再打开新版；仅关闭窗口可能仍留在后台。此次没有结束用户已有会话，没有把截图中已排队的消息重发或改投其他会话。

源码和锁的跨进程测试不等于已对用户当前旧窗口做现场修复；原生重复启动提示框尚未在当前桌面点验。模型验收使用独立临时目录和独立会话，只停止测试自身创建的进程。其他平台和所有 Runtime 两两组合不属于此次真实验收范围。

## Codex 延迟收件追加修复（2026-11-08）

现场当前只有一个桌面主实例。恢复窗口、打开指南导致终端重新布局后，旧队列开始处理；没有重新发信。这说明恢复操作能触发投递，不等于现场问题已经永久消失，也不能据此断言只是模型正常等待。

失败回归明确复现了：Codex 的合法 AgentTurnComplete 已接受，但上一轮的终端 busy blocker 仍使 is_ready_for_prompt 为 false。真实 Codex 0.167 的隔离输出还显示，完成 hook 之后仍可能出现 Working/Running hooks，随后由 OSC 7501 通知 idle/working/done。

- 将忙碌标记与权限、登录、更新等弹窗分开；完成 hook 只释放忙碌标记。弹窗继续等待明确的新输入提示。
- 识别完整 Codex OSC 状态，兼容 BEL 和 ST 结尾及跨块输入；后出现的忙碌画面优先于旧空闲信号，清屏后不沿用旧状态。
- 已完成的 Codex 不因游标、颜色和局部页脚重绘丢失收件就绪；派发后仍消费就绪，未知新画面仍撤销就绪。
- “Claude 向 Codex 打招呼”按定向通信处理；发送者拼写不明确时返回错误，不再悄悄广播给两方。

中间版本全量 Rust 1027 通过、38 忽略，包含权限弹窗、更新菜单、拆分状态、旧忙碌尾帧、派发消费以及未知清屏回归。窄终端（Codex 60 列）与延迟来信的真实四轮往返基线通过，基线没有稳定复现现场长延迟，因此只把它作为真实接收链路回归。
