# 三种协作玩法

把 Agent 按任务组织起来：一个实现，一个审查，需要时再交接给另一个继续。

下面是操作示例，不是已经运行的演示记录。先在可信的演示项目中使用，并保留各 Agent 原有的权限选择；模型调用使用你自己的账号与配置。

[返回首页](../README.md) · [完整使用手册](user-guide.md)

## 先把队友准备好

1. 在系统终端确认要使用的 Agent CLI 已安装、登录且能够独立使用。
2. 在 CrewVela 创建相应会话，选择工作目录。第一次可以只开两个，分别命名为「功能实现」和「代码审查」。
3. 从左侧「会话通信」核对发送方、接收方和实际会话；项目协作也可以选择同一项目的成员。多个同名对象时先明确目标。
4. 使用指南为当前对象生成的指令。旧会话若没有加载通信工具，重新打开后再核对。

## 玩法一：一个实现，一个审查

**适合：** 新增一个功能、修一个 Bug，想让另一个 Agent 再看一遍。

| 角色 | 工作 |
| --- | --- |
| 功能实现 | 理解需求，修改代码，说明差异、验证结果和未完成项 |
| 代码审查 | 查看明确的改动范围，指出问题、影响及复现步骤 |
| 你 | 决定哪些建议采纳、何时扩大范围或结束任务 |

给「功能实现」一个具体任务，例如：

> 给演示项目的待办列表增加完成状态筛选。先查看现有实现，只修改相关内容，验证已完成、未完成和全部三种状态。完成后说明改动和验证结果。

需要审查时，在发送方提出：

> 请先核对当前已打开的会话，找到「代码审查」。把本次任务、修改文件、差异摘要和验证结果发给它，请它审查潜在问题，只联系这个会话。发送前不要附带密钥、账号或私人日志。

审查者应检查实际交付，而不是只接受摘要。若双方使用不同 worktree，应同时说明分支或提交，以及如何读取该份改动，避免审查另一份工作区。根据审查结果，再由实现者处理并重新验证。

## 玩法二：保留原思路，换个 Agent 继续

**适合：** 需要第二种实现思路，或希望把下一阶段交给另一个 Agent。

1. 在来源会话菜单中选择交接，指定接手 Agent。
2. 先准备、预览交接资料：目标、已完成工作、未完成项、文件与分支、验证结果、需要人工决定的问题。
3. 核对工作目录与交付范围，再确认交接。
4. 接手 Agent 继续处理；回看来源会话历史，对照原要求。

当前流程会停止来源会话并保留其可见历史。目标按自身原生能力和权限设置启动，不继承来源的 YOLO、排队请求或待审批操作。交接资料可能截断，接手者仍需核实计划和验证结果。

## 玩法三：按角色推进一个项目

**适合：** 一个需求可以拆成实现、审查和集成等相互依赖的任务。

在多智能体协作入口描述目标与分工，例如：

> 为演示项目增加一页任务看板。一个成员负责页面实现，另一个负责代码审查；说明任务依赖和验收方式，先给我查看计划，再启动执行。

确认成员、运行时、目录与任务依赖后再启动。通过工作台查看当前任务、成员会话、协作消息与诊断；需要两名成员直接对齐时，从「会话通信」选择项目成员。

并行写入时按需使用独立 worktree，并约定交付方式。先核对各分支的改动与验证结果，再决定如何集成，避免两个成员同时改同一份工作目录中的同一文件。

如果目标和验收条件已经明确，可以从输入框工具菜单选择「全自动托管」。一个成员可完成实现和交付，多名成员可按任务安排开发、审查与联调。要求独立审查时，选择能担任只读审查的成员，并在交付卡片核对验收结果和对应提交。需要停止或人工介入时，通过任务执行记录查看原因及当前状态。

## 怎么知道消息真的过去了

- **复制了指令**：只进入剪贴板，没有发送。
- **显示已排队**：进入队列，尚不表示目标已收到或回复。
- **目标会话可见消息**：到正确的目标会话核对来源和内容。
- **收到回复**：核对回复者及所回答的问题，避免把状态通知当成结果。

对方忙碌时可能等待。长时间没有变化，先打开通信诊断，查看会话是否仍在运行、是否等待授权、是否加载工具，以及有没有投递错误；不要不断重发同一条指令。
