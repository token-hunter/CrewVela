# CrewVela 的多 Agent 自动交付，下一步做什么

2026-11-19。建议首先让**测试结果绑定实际交付的 Git 提交**，随后做**不同成员之间的接口验收**，最后补上**交付中断后的核对与续办**。这三件事解决不同的问题：交的是不是测过的版本、各成员的成果拼起来能不能用、应用掉线后要不要重做。最适合对用户演示的是第二项，第一项则是另外两项可信的基础。

## 现成的东西已经不少

核查对象是 CrewVela 本地 `fa8adfc` 所在工作区。当前工作区包含尚未提交的全自动托管实现；以下谈的是这里的代码。自动交付的终点按现有实现指**合入授权的本地项目分支并登记结果**。推送远端、部署生产、验证线上服务是后续不同的操作。

| 已有机制 | 值得增补的一小步 |
|---|---|
| 分工计划已经查依赖环和并行写入范围；符合条件的跨 Runtime 并行开发要配独立只读审查和集成。已有成员库、角色、分工卡和项目群聊可作为操作入口。[分工检查](../../src-tauri/src/multi_agent/conversation.rs#L2228) · [交叉审查](../../src-tauri/src/multi_agent/plan_validation.rs#L58) | 即便文件完全不重叠，两个成员对同一个接口也可能各有理解。给高风险配合点留一个可运行的共同样例。 |
| 任务有独立工作树、依赖产物和提交哈希，集成可以取审查过的产物链。托管会检查测试实际执行、写入范围、目标分支和基线，目标变化时拒绝快进。[执行与检查](../../src-tauri/src/multi_agent/executor.rs#L2211) · [目标分支保护](../../src-tauri/src/multi_agent/managed_delivery.rs#L62) | 把这次测试对应的**候选提交**也记录下来，区分“有测试通过、有一笔提交”和“这笔提交通过了测试”。 |
| 已有定向返工、重试上限、任务树停止时的独立复核、人工干预、运行日志。托管启动恢复会保留现场，对未结束计划登记失败。[任务复核](../../src-tauri/src/multi_agent/governance.rs#L209) · [返工测试](../../src-tauri/src/multi_agent/store.rs#L7664) · [启动恢复](../../src-tauri/src/multi_agent/managed_delivery.rs#L401) | 在“合入分支”和“写入完成记录”之间留一份可核对的意图，让恢复程序判断究竟是哪一步没完成。 |

## 外部经验怎样影响了判断

- **多个成员各自表现好，组合仍可能失败。** CooperBench 把可能互相影响的开发任务分给两个 Agent；其特定样本中，协作表现平均逊于同一 Agent 承担两项工作。AsynCodeBench 更进一步，给跨成员的依赖单独写可执行检查，观察到任务整体指标与依赖是否真正接通可能分歧。对 CrewVela 的启发是单独验“接口两端能否一起工作”。这些实验不能推算 CrewVela 的失败率。[CooperBench](https://arxiv.org/abs/2601.13295) · [AsynCodeBench](https://arxiv.org/abs/2609.32662)
- **合并结果是独立的测试对象。** GitHub Merge Queue 会在目标分支和排在前面的改动组合后执行必要检查，组合失败就移出队列。CrewVela 已经有本地 Git 工作树和集成者，可直接对组合后的候选提交运行验收；仅为了学这个原则，无需再建一套 PR 队列。[GitHub Merge Queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)
- **一个 Agent 缺席或没回话，不能据此判断代码是否已交。** Orca 的一位用户报告过工作已提交、协调者却一直等完成回报的情形。LangGraph 的检查点文档也区分已落盘的步骤和恢复时必须重做的步骤。对 CrewVela 有用的是凭证据决定“重做、补记、交人判断”。前者是个案，并非对 Orca 当前版本的故障定论。[Orca 用户报告](https://github.com/stablyai/orca/issues/14829) · [LangGraph 持久执行](https://docs.langchain.com/oss/python/langgraph/persistence)
- **协作的成本也应测。** Cursor 的长期编码实验记录了文件锁阻塞和成员偏向容易任务的问题；Anthropic 的研究系统记录过小问题被拆给过多子 Agent、多个成员重复搜索。CrewVela 已有职责和任务边界，下一步更值得比较“哪些任务加入第二个人真的少返工”，而非把固定人数变成每个任务的开销。[Cursor 工程实验](https://cursor.com/blog/scaling-agents) · [Anthropic 工程实践](https://www.anthropic.com/research/multi-agent-research-system)

## 本机做了两个独立对照

使用临时 Git 仓库、真实 Git 工作树和 Node 测试，使用固定代码变更模拟两个成员。以下是可重复的机制实验，未启动真实模型或走 CrewVela 桌面端。

| 场景 | 观测结果 |
|---|---|
| **两个独立变更，各自通过，合在一起失败。** 基线 API 同时返回 `customer_id` 和旧名 `customerId`。一个成员删除旧字段，另一个成员简化导出代码，只读旧字段。两人改不同文件，预期业务行为是导出客户编号 `00123`。 | 基线、只合后端、只合前端，各自均 **3/3**。两个变更合并时 Git 无冲突，组合后的两项组件测试 **2/2**；真实 API 接 CSV 导出的测试 **0/1**。改回读取规范字段后 **3/3**。同一条接口测试要在组合版本上再跑才抓得到。 |
| **同一条测试，测试时和交付时结果不同。** 初始设置为 5，断言通过；在测试结束、保存交付前模拟一次受版本控制的文件写入，把设置改为 4，然后提交。 | 旧内容 **1/1**，候选提交重跑 **0/1**。源码也存在先执行 `verify_task_acceptance`、后调用 `checkpoint_task_workspace`、再快进的顺序。实验验证这个时间差的后果，没有统计真实用户遇到的频率。[验收顺序](../../src-tauri/src/multi_agent/executor.rs#L2212) · [保存提交](../../src-tauri/src/multi_agent/executor.rs#L2464) |

另用当前源码跑了 5 项原有 Rust 回归，全部通过：托管计划经审查与测试交付、并行写入重叠拦截、任务树停止后只启动一次语义复核、集成保留审计提交链、返工预算耗尽后停止。托管用例使用真实 Git 和 Node、模拟成员输出。已有的成功路径与本次研究的故障窗口可以同时成立。[托管回归](../../src-tauri/src/multi_agent/conversation_tests.rs#L1783) · [产物链回归](../../src-tauri/src/multi_agent/executor.rs#L8076)

## 三项建议怎样落到已有产品上

### 1. 每次自动交付都回答“验收的是哪个版本”

在现有集成交付步骤先检查范围、固定候选提交，再在与该提交对应的工作树运行项目已有的验收命令。记录任务、运行、命令、退出结果、日志引用、候选 SHA 与目标基线。合入时重查目标仍是授权基线、候选版本与证据一致。协作中心打开已有交付记录时，用户应能直接看见“哪一版、哪条测试、有无未验项”。可先只覆盖托管的最终集成，保留普通开发迭代的速度及现有范围保护。[现有验收器](../../src-tauri/src/multi_agent/executor.rs#L2900) · [已有交付清点](../../src-tauri/src/multi_agent/managed_delivery.rs#L299)

验收至少覆盖四种情况：正常候选通过并仅合入该 SHA；测试修改受版本控制的源码时拒绝该证据；测试产生被忽略的正常缓存不误报；目标分支在测试期间前进时保留候选、停止合入。若用干净检出，还要处理依赖与生成物，使正常项目在相同环境中能复跑；若复用原工作树，则需处理未跟踪且会影响测试的文件。回执只能说明给定检查在给定环境和版本上的结果，不能证明验收覆盖了所有需求。

### 2. 让“交给下一位”附一个双方都能运行的样例

这是最值得形成 CrewVela 产品辨识度的一项。在现有分工卡的具体依赖旁，为涉及 API、数据格式、迁移或前后端联动的任务补三件事：**谁提供、谁使用、用哪个输入能证明两边接通**。提供方记录样例和约定，使用方可补一个反例或引用仓库已有测试；集成成员在两边代码都存在的候选提交上实际运行。多数纯文案或独立任务无需添加此项。

复用任务依赖、项目测试、验收命令和现有返工操作。首次检查失败，在原任务记录里指出失败样例、两边的提交和原始日志；可以先由原集成成员或人决定修哪一边，避免把“最先报错的一方”自动判责。两个成员改不同文件但接口错配的例子是验收样本；单个提交回滚后测试应恢复，对照一个无关组件变更，不应无故重派整个团队。第一版只选一个仓库、一个真实接口、一个已有测试入口。

这也是团队和共享记忆可以一起发挥作用的地方。如果这次失败真的促成一次修复、经审查并在最终提交上跑绿，可以把**为什么需要这条用例、测试路径、适用模块和来源提交**附到项目经验里。下次同一团队修改该接口时，在生成分工的阶段提示“上次丢过前导零，要不要复用这项验收？”；代码已经迁移、旧测试不存在时提示复核，不自动把过期经验当新需求。默认团队可以跨项目复用，客户编号等业务事实仍留在所属项目。这里适合复用现有项目经验工具，设计时先明确哪份记录是来源，不要求与 ai-memory Wiki 全量双写。[项目协作记忆](../../src-tauri/src/multi_agent/bridge.rs#L473) · [默认团队复用](../../src/components/CollaborationMemberLibrary.tsx#L138)

### 3. 自动交付中断后，只补真正没做完的那一步

当前托管路径先快进 Git，再在 SQLite 登记任务成功；重启时会把未结束的计划标为失败。这里有一个窄但具体的窗口：分支已经到了正确提交，应用却来不及落账。建议先在现有本地存储记录“准备把哪个候选合入哪条分支”，和第一项验收记录关联。恢复时检查这条分支、基线、候选及实际 HEAD。若分支已在候选且验收证据齐备，只补登记；若仍在基线，则结合原授权状态、暂停/撤销状态决定是否可继续；若用户另有提交、进程状态未知或证据不足，保留现场，交给现有干预入口。任务重试必须复用同一交付标识，避免重复合入或重复宣布成功。[Git 合入和运行登记](../../src-tauri/src/multi_agent/executor.rs#L2255) · [托管启动恢复](../../src-tauri/src/multi_agent/managed_delivery.rs#L401)

验收用故障注入，分别在写意图后、合入后、登记后终止进程，再连续恢复两次。核对 Git、任务状态与交付事件一致；已有正确提交不重复执行 Agent；手动移动分支、取消计划及缺少验收记录的反例不得自动确认成功。本轮从源码定位了这个窗口，没有做应用崩溃复现。

## 怎样判断投入是否值得

首轮选一个前后端共用接口的项目，对比现有托管流程与上述改进，用相同项目快照、相同模型配置、成对任务，分别记录：

| 观察项 | 判读方式 |
|---|---|
| 报完成却不能使用 | 以用户实际操作或独立集成检查复核。保留失败样例和被宣布成功的提交。 |
| 交付证据是否对应成品 | 已交付提交与验收 SHA 对不上或没有证据的次数。第一项上线门槛为设定故障样本中零误放行。 |
| 返工范围 | 一处接口失败后，重跑了多少无关任务、额外用了多少分钟或模型调用。简单任务也做对照，避免收益只出现在刻意设计的复杂样本。 |
| 恢复是否可靠 | 区分正确补记、重复执行、错误宣布成功和转人工四类。无法判断时转人工的次数单列，不能拿更激进的自动确认率当改进。 |

开发顺序建议 **1 → 2 → 3**。如果当前用户最常抱怨“隔夜回来不知道到底交没交”，则把第 3 项提前到第 1 项之后。先把证据落到现有任务与交付记录，再根据真实使用决定是否需要新界面。这次没有对真实账号、生产环境部署或不同平台的运行结果作验收。
