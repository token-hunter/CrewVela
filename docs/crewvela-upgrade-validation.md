## 通信故障

已用同一隔离 CLI 子进程复现：普通进程可以排队，Codex 只读 sandbox 写 outbox 时发生 `os error 5`。不是把模型输出的“完整对话”当作消息送达证据。

修复在普通交互 Codex 启动前读取有效权限，派生仅给消息 outbox 增加写权限的配置，保留原 profile 继承、网络策略和用户全局配置；遇到明确 deny 时不扩大权限。未知隐式策略保持原命令，不添加额外目录、不猜测或替换原安全策略；此情况下不保证只读沙箱内的 CLI 消息可写。原始进程需要恢复或重启后才能加载新环境与权限。

短参数连写、等号形式和 `--` 分隔符已统一处理；探测时不把提示正文当作配置，新增权限参数放在分隔符之前。真实矩阵覆盖 13 组参数/配置场景及 2 组字面提示场景。`--approve-for-me` 及其别名保留本机 Codex 的原审批语义，不覆盖原有只读命名权限。三个可能触发探测的 IPC 入口已转后台调度，新增 8 线程同时领取自动化任务的测试验证不会重复领取。

当前明确限制：本机 Codex 的 app-server 无法等价探测 `-p/--profile` 文件层，所有这些形式均安全拒绝且原命令不变；旧版 `--full-auto` 和含 glob 元字符的 outbox 路径也明确拒绝。通过 `default_permissions` 选择的命名权限配置仍支持。不能把 profile 内容提升为 CLI 最高优先级来假装继承成功，也不自动降级为全权限。RPC 响应接收有 10 秒超时；这不代表子进程写入和退出的整个生命周期都有同一绝对时间上限。

仓库的 `skills/crewvela/SKILL.md` 已同步新环境名，并明确“排队不等于送达或对方回复”，禁止编造对话或改用全权限绕过失败。

本机发现已有全局通信 Skill 副本仍是旧版。为避免破坏仍运行旧应用的会话，本次没有覆盖该全局文件。升级时应将本仓库的通信 Skill 同步到 Claude Code/Codex 实际使用的 Skill 目录，再用新构建恢复原会话；若 `.agents/skills/crewvela` 是指向另一个目录的 junction，应更新其实际目标，不创建第二份冲突副本。

## 设置尺寸

各菜单原本使用不同正文宽度和边距，721–760px 还存在旧样式隐藏导航的问题。现在所有设置菜单使用统一公共边界，归档长列表只滚动正文，保留导航。公共选择器覆盖组件样式的加载顺序，避免共享记忆在窄屏及异步加载时重新覆盖正文宽度。

实际浏览器验证覆盖 687/720/740/760/820/1440/1920 像素宽度、明暗主题、空归档及 100 条归档，共 28 个组合、420 次菜单访问；另外在实际应用预览逐项点击 15 个菜单，边界相同且根节点不溢出。原生 Tauri 验收使用独立 WebView2 宿主和临时数据目录，不启动主应用业务状态，不影响用户正在运行的旧版。

已在 Windows 原生 WebView2 宿主逐项点击全部 15 个菜单并查看 100 条归档页面。原生日志从创建到关闭均为物理外框 1818×1172、客户区 1800×1125、缩放 1.25，没有菜单触发的 resize/scale 事件。CUA 截图按其显示比例输出 1442×931，切换前后相同；这两个数字是不同测量单位，不能把截图显示尺寸当作原生物理尺寸。设置布局验收当时，真实用户窗口仍运行旧构建且保持未改动；后续 Codex 热修复的正常重启记录见文末。

该独立宿主故意不注册业务命令，Git 等页面会显示命令未注册的错误提示；没有隐藏错误。这次原生验收只证明实际 WebView2 中的菜单切换和外框稳定，不代表全部设置功能已通过原生端到端验收。
